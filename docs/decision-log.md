# 결정 기록

"어느 위치·어느 데스크탑에서든 항상 접근 가능한 개발환경"을 만들기까지 검토한 선택지와,
어떤 근거로 접었는지에 대한 기록. 2026-08-19.

---

## 결정 1 — 새로 만들지 않고 Orca의 Remote Server 모드를 쓴다

조사해보니 Orca에는 이미 이 요구사항을 위한 기능이 있었다. 별도 인프라를 설계할 이유가 없었다.

- `orca serve` — 데스크탑 창 없이 런타임 서버만 기동 (헤드리스 서버용으로 문서화됨)
- `orca environment add --pairing-code` — 다른 기기에서 그 런타임에 클라이언트로 접속
- 웹 클라이언트 번들이 앱에 포함되어 있음 (`out/web/web-index.html`).
  로컬 런타임에 `GET /web-index.html` 요청 시 200 응답을 실측으로 확인 → **브라우저만으로 접속하는 경로가 실재함**
- Linux 빌드(AppImage / deb / rpm, x64 및 arm64)가 릴리스에 존재 → 클라우드 VM에서 구동 가능

공식 문서상 실행 방식은 네 가지 — 로컬 데스크탑 / SSH 타깃 / **Remote Orca Server** / 워크스페이스별 클라우드 VM.
"에이전트를 24/7 돌리고, 여러 기기에서 같은 세션에 다시 붙는" 요구에 해당하는 것은 세 번째다.

## 결정 2 — 호스트를 개인 PC에서 클라우드로 옮긴다 (방향 전환)

**처음 방향**: 개인 데스크탑을 상시 호스트로 쓰고 Tailscale로 접근. 비용 0이고 기존 상태
(에이전트 계정, orchestration DB, 워크트리)가 그대로 유지된다는 장점이 있었다.

**전환 이유**: 구축 도중 해당 PC의 이더넷 어댑터에 **공인 IP가 NAT 없이 직접 붙어 있는 것**을 발견했다.
게다가 과거 Windows 방화벽 팝업에서 "허용"을 누른 흔적으로 `orca.exe`에 대해
**모든 포트 / 모든 원격 주소**를 허용하는 인바운드 규칙 2개(TCP·UDP)가 Public 프로파일에 살아 있었고,
런타임은 `0.0.0.0:4224`로 리슨 중이었다.

즉 개인 PC를 원격 개발 호스트로 쓰는 방향은 "집에 있는 기계를 인터넷 쪽으로 조금씩 여는" 일이 된다.
사용자 판단은 명확했다 — **개인 PC의 네트워크는 건드리지 않는다.**

**조치** (실행 완료)
- 문제의 인바운드 허용 규칙 2개 삭제 → 이후 4224를 여는 인바운드 허용 규칙 0개 확인
- 검토 중 설치했던 Tailscale 제거 (서비스·어댑터·설치 폴더 잔여물 없음 확인)
- 등록했던 자동시작·워치독 예약 작업 제거

**결과 원칙**: 노출되는 대상은 개인 PC가 아니라 언제든 갈아엎을 수 있는 격리된 VM이어야 한다.
그리고 **접속하는 쪽 PC는 아무것도 설치·변경하지 않는다** — VPN 클라이언트조차 전제하지 않는다.
이 원칙 때문에 Tailscale 기반 설계는 전부 폐기됐다. tailnet은 접속하는 기기도 가입해야 성립하기 때문이다.

대안은 서버 쪽에서 HTTPS/WSS로 종단하는 것 — 리버스 프록시(Caddy) + 자동 TLS.
클라이언트는 URL 하나와 페어링 링크만 있으면 된다.

## 결정 3 — Lightsail 4GB (x86)

24/7 상시 가동을 전제로 서울 리전 기준 비교:

| | Lightsail 4GB | EC2 t4g.medium (Graviton) | EC2 t3.medium (x86) |
|---|---|---|---|
| 컴퓨트 | **$24/mo 정액** | $0.0416/h ≈ $30 | $0.052/h ≈ $38 |
| 스토리지 80GB | 포함 | gp3 별도 ≈ $7 | gp3 별도 ≈ $7 |
| 공인 IPv4 | 포함 | 별도 ≈ $3.6 | 별도 ≈ $3.6 |
| 아웃바운드 전송 | 4TB 포함 | 100GB 무료 후 과금 | 동일 |
| **합계** | **≈ $24** | **≈ $41** | **≈ $49** |

**EC2를 접은 이유** — EC2의 최대 장점은 "안 쓸 때 끄기"인데, 목표 자체가 상시 가동이라 쓸 수 없는 카드다.
1년 Savings Plan을 걸어도 t4g 기준 $30 언저리로 여전히 비싸고 1년이 묶인다.
EC2가 맞는 경우는 기존 VPC 내부 리소스에 사설 IP로 붙어야 하거나, 나중에 GPU·대형 인스턴스로
갈 여지를 남길 때다. 개발 호스트 1대에는 해당하지 않는다.

**Graviton을 접은 이유** — Orca 자체는 arm64를 공식 지원한다(arm64 deb/AppImage/rpm, `relay/linux-arm64` 번들 확인).
문제는 두 가지다.

1. **Lightsail에는 ARM 번들이 없다.** 서울 리전 `get-bundles` API와 공식 번들 문서 확인 결과
   Linux/Unix·Windows 구분만 있고 아키텍처 선택지가 없다. Graviton을 쓰려면 EC2로 가야 하는데,
   그러면 ARM으로 아끼는 20%(연 $96)를 EBS·IPv4 부가비용(연 $127)이 그대로 먹는다.
2. **개발 호스트로서 아키텍처 불일치 리스크.** amd64 전용 Docker 이미지는 ARM에서 QEMU 에뮬레이션으로
   현저히 느려지고, 배포 대상이 x86이면 빌드 아티팩트도 어긋난다. 호스트를 배포 대상과 같은 x86으로
   맞추는 편이 사고를 줄인다.

**IPv6 전용 번들 검토** — Lightsail에는 IPv6 전용 4GB 번들이 $20/mo로 존재한다($4 저렴).
공개 포트를 최소화하는 설계라 공인 IPv4가 꼭 필요하진 않지만, 부팅 초기 접속 경로가
Lightsail 브라우저 콘솔 하나로 줄어든다. **월 $4에 복구 경로를 줄이는 건 남는 거래가 아니라고 판단**하여
IPv4 포함 번들($24)을 선택했다.

## 결정 4 — 접근 경로는 서버 쪽 HTTPS 종단

Orca 런타임은 평문 WebSocket이다. 브라우저는 HTTPS 페이지에서 평문 ws로 붙는 것을 차단하므로
(앱 내부 오류 메시지로 확인), 브라우저 접속을 지원하려면 wss 종단이 필수다.

Caddy를 443에 두고 127.0.0.1:4224로 리버스 프록시하면 세 가지가 한 번에 해결된다.

1. 브라우저에서 접속 가능 (설치 불가 PC 대응)
2. 인증서 자동 발급·갱신
3. 런타임 포트를 인터넷에 직접 노출하지 않음 (Lightsail 방화벽에서 4224 미개방)

**남는 트레이드오프**: 443은 인터넷에 공개된다. 방어선은 Orca 페어링 토큰이며, 필요 시
Caddy basic_auth를 한 겹 더 얹는다. 다만 노출되는 대상이 개인 PC가 아니라 스냅샷으로 되돌릴 수 있는
VM이라는 점에서 처음 방향과 위험의 성격이 다르다.
